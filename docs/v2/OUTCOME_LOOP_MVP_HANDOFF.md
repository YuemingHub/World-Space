## 2. MVP 实际结构（比原计划更薄）

```text
真实意图（一句话）
   ↓  /api/world  （护栏在前，认知链不变）
契约新增一个字段与一个输入：
   next_action { text, done_when, mode, handoff_task, handoff_target }   ← 本轮唯一主行动
   receipt      { status: done|stuck|info, text }                        ← 用户带回的现实结果
   ↓
结果页只回答一件事：「现在只做这一步」
   主行动 + 怎么算做完（可验证的 done_when）+ 这一步谁来做（internal / handoff / human）
   handoff 时：完整任务书（复制→粘贴→直接用）+ 白名单跳转（第一版只有 DeepSeek 官方入口）
   交棒链接永远来自前端代码，模型只给目标名；匹配不上就不给"打开"按钮
   ↓
用户去做（离开页面：打电话 / 去窗口 / 用外部 AI；或在本页完成分析）
   ↓
「去做，然后把结果带回来」：做成了 ✓ / 卡住了 / 粘贴结果（可粘贴原文）
   ↓
回执原样进入下一轮模型上下文（meta 如实标记 receipt_ingested / receipt_status）
   提示词硬规则：带回执时禁止重答原始意图、禁止重复上一轮路径；原路不通必须换下一责任方或换方法
   ↓
下一轮：新的"现在只做这一步"
```

**执行模式语义**（第一版只有三种，不造更多）：
`internal` 这一页就能完成的分析/整理；`handoff` 交给现成外部工具更合适（必须附完整任务书，空手交棒自动降级 internal）；
`human` 必须本人进入现实世界（打电话、去窗口、见面、现场记录）。

**状态**：只有本机 localStorage 一个键（意图 + 上一份契约 + 更新时间，7 天后丢弃），刷新/回来接着上次继续。
**没有**：账号、数据库、云同步、浏览器扩展、跨站 DOM 读取、屏幕监控、任何"用户点了哪个按钮"的遥测。

## 3. 为什么保持这么轻

- 新增任何东西先过一道问：**它是否明显提高用户拿到现实结果的概率**。提高不了的不做。
- 交棒不造自动化：不接管用户的外部会话、不读第三方页面，只给"准备好的任务 + 官方入口 + 回来贴结果"。
  宁可复制粘贴是真的，不要一套自动执行架构但还不能用。
- 一轮只给一个动作：结果页 DOM 审计确认全程只有 1 个 `.action` 块（浏览器旅程实测）。
- 回执是这一轮唯一的新交互，且它必须真的改变下一轮——不是页面上的装饰（差分回归 + 真实旅程双重证明）。

## 7. 还有哪些真实限制

1. **主动 handoff 未被真实触发**（L19）：机制齐全但真实模型更愿意用本页能力完成；需要真实用户证据再判断要不要调整倾向。
2. 行动回路状态只在本机、7 天后丢弃；换设备/清缓存即断（第一版有意如此，不上云）。
3. 受控浏览器环境缺陷使"截图级视觉证据"与"127.0.0.1 源持久化"无法在 IAB 内验证；真实浏览器需 Founder 复核一次。
4. 深夜网关抖动会造成一轮 502（诚实失败 + 可重试），无多路由/重试编排（明确不做）。
5. 单实例部署语义（预留式预算准入、内存限流）不变；多实例需集中配额。
6. 长链（三轮以上）与"回执里贴超长外部对话"只做了截断（2000 字），未压测语义质量。
7. Tavily 旧 key 仍未轮换（生产部署前必须执行，非本轮范围）；方舟 key 未修，主模型仍为 deepseek-flash 旧网关。
8. 延迟 p50 仍在 35-90s（理解+搜索+生成串行），前端有诚实 loading。
